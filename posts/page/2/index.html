vLLM-Ascend KV cache：固定版本证据素材

核实版本：v0.21.0rc1，提交 80610e4438dba05011b05f89fc45d91e96992671。以下限定该版本及所指 backend，不代表全部 Ascend 硬件、模型或最新 main。

代码类型：第 1、2、3、6 段为短原码；第 4、5、7 段为独立编写的教学伪代码，不能直接运行。

1. Runner 继承与 Spec 来源

原码：类声明，省略类体。

class NPUModelRunner(GPUModelRunner):

常规层的 Spec 来自上游 vllm.v1.kv_cache_interface，由层的 get_kv_cache_spec() 汇集；MLA 有 Ascend 扩展。此处继承的是 runner，不能据此声称所有 Spec 都完全未改。继承入口、Spec 汇集。

2. 分配、建立视图、绑定

原码摘句：三句来自不同位置，不是连续函数。

return torch.zeros(numel, dtype=torch.int8, device=self.device)
kv_caches = self._reshape_kv_cache_tensors(kv_cache_config, kv_cache_raw_tensors)
bind_kv_cache(kv_caches, self.compilation_config.static_forward_context, self.kv_caches, num_attn_module)

raw int8 是字节容器，随后按缓存 dtype 建视图，并不表示全部 KV 都做 INT8 量化。一般 K/V 分配分开；启用 KV 传输时地址按 2 MiB 对齐。初始化管线、分配入口、视图建立。

结论：GPU 路径把 KV 缓存分成三个主要层次：spec 描述每层需要多少缓存、何种保留规则；manager 决定请求使用哪些物理块；attention backend 决定这些字节如何排列及读写。因此 KVCacheSpec 既不是实际 tensor，也不是完整的编译图或硬件布局描述。
