    GPU vLLM V1：KVCacheSpec 设计证据与图例素材

    核查日期：2026-10-18。分析对象是本地 /home/daniel/code/houmo/houmo-vllm-18f6bf5/ 中的 V1 GPU 路径。本文件只整理已读取源码的行为，没有在 GPU 上运行推理、profile 或性能测试；数值例与寻址例均为公式演算。

    结论：GPU 路径把 KV 缓存分成三个主要层次：spec 描述每层需要多少缓存、何种保留规则；manager 决定请求使用哪些物理块；attention backend 决定这些字节如何排列及读写。因此 KVCacheSpec 既不是实际 tensor，也不是完整的编译图或硬件布局描述。

    2. Spec、Group、Tensor、Config 各自解决什么问题

    对象粒度与责任不负责的内容
    KVCacheSpec单层缓存格式和容量接口；block_size 表示一块覆盖多少逻辑 token不保存请求 ID、block table、tensor 指针
    AttentionSpec / FullAttentionSpec记录本地 KV head 数、head dimension、dtype、量化附加开销、页大小与最大需求不固定物理轴顺序
    KVCacheGroupSpec一组共享 block table 的层；缓存管理器把该组视作一个管理单位同组不意味着层间复用同一份 K/V 数值
    KVCacheTensor一块底层 tensor 的字节总量，以及哪些层使用这块存储池不直接记录请求目前占据其中哪几页
    KVCacheConfignum_blocks、各 tensor 分配计划和分组计划还不是实际设备 tensor
    BlockPool / manager管理 block ID、引用计数、前缀命中、释放和淘汰不决定 CUDA kernel 的数据排布
    attention backendget_kv_cache_shape() / stride、缓存写入 kernel、attention 读取不独自决定全局显存预算和请求准入

    定义见 kv_cache_interface.py:95、AttentionSpec:143、KVCacheTensor / Group / Config:792。

    代码摘录 1：普通 Full attention 的单层页字节数

    以下是 FullAttentionSpec.real_page_size_bytes 非 NVFP4 分支的原文，来源 kv_cache_interface.py:293，第 293–298 行：

    return (
    self.block_size
    * self.num_kv_heads
    * (self.head_size + self.head_size_v)
    * get_dtype_size(self.dtype)
)

    重要的是它返回字节数，而不是某个固定 shape；K、V 的 head dimension 也允许不同。

    3. 容量公式与完整数值例

    令 B 为每块 token 数，H 为本 rank 的 KV head 数，Dk/Dv 为 K/V 每个 head 的维度，S 为每元素字节数，L 为本 worker 上的层数。普通未量化 Full attention：

    [ P_{layer}=B\times H\times(D_k+D_v)\times S ]

    在所有层规格相同、只有一个 KV group 的常见情形，一个 block ID 在所有层上对应的总容量为：

    [ P_{pool}=L\times P_{layer},\qquad N_{blocks}=\left\lfloor\frac{M_{available}}{P_{pool}}\right\rfloor ]

    实现见 get_num_blocks:930。这不意味着这些层的内存一定合并成一个张量；它首先是调度器统一分配一个 block ID 所对应的容量成本。

    取 B=16,H=8,Dk=Dv=128,S=2(BF16),L=32：

    项目计算结果
    单层单页16 × 8 × (128 + 128) × 265,536 B = 64 KiB
    32 层一个 block ID32 × 64 KiB2 MiB
    已算出的 KV 可用预算假设已经扣完其他显存16 GiB
    可配置 block ID 数16 GiB / 2 MiB8192
    普通请求可使用的块数池保留 block_id=0 为 null block8191
    一个 8192-token 请求ceil(8192/16) × 2 MiB1 GiB

    该例仅用于理解公式，不代表 Houmo 或某个真实模型的测量结果。多请求最后一块不满、hybrid padding、量化 scales、前缀共享都会改变实际有效容量。

    几个容易误算的地方：

    • H 是分片后的本地 head 数。Llama 示例在 TP 足够大、KV heads 少于 TP 时会复制 KV heads，采用 max(1, total_num_kv_heads // tp_size)，不能无条件使用整模型 head 数再除任意 TP。见 llama.py:142。
    • AttentionSpec.page_size_bytes 还会计入 per-token-head scales：K/V 各一个 FP32 scale，共 2 × B × H × 4 字节；page_size_padded 可继续扩大页。见 kv_cache_interface.py:152。
    • MLA 缓存与普通独立 K/V 的形式不同，不能总乘 2；该版本还区分 storage_block_size 与逻辑 block_size。见 MLAAttentionSpec:349。
    • Full attention 的单请求最大需求为 ceil(max_model_len / B) × page_size_bytes；启用 context parallel 时需先按其实现调整本地保存长度。见 max_memory_usage_bytes:210。

    4. 从模型规格到实际 CUDA tensor 的链条

    代码摘录 2：Attention 层返回规格

    来源 attention.py:575，第 575–582 行：

    return FullAttentionSpec(
    block_size=block_size,
    num_kv_heads=self.num_kv_heads,
    head_size=self.head_size,
    head_size_v=self.head_size_v,
    dtype=self.kv_cache_torch_dtype,
    kv_quant_mode=quant_mode,
)

    Runner 从 static forward context 枚举 attention 模块并调用此接口，得到 dict[layer_name, KVCacheSpec]。跨层共享 KV 的 follower 会跳过独立 spec，避免重复预算；见 gpu_model_runner.py:7088。

    Engine 依次收集规格、询问各 worker 可用内存、生成配置、初始化 worker。对应 engine/core.py:232。GPU worker 默认运行 profile，把权重、activation 峰值、非 Torch 开销及可选 CUDA graph 预算从 requested memory 中扣除；也支持显式 kv_cache_memory_bytes。见 gpu_worker.py:354、预算计算:443。

    跨 worker 的配置先全局分组，再按 PP 各阶段持有的层投影，最后将所有 worker 的 num_blocks 收敛到最小值，并同比缩小 tensor 分配。这样同一个中心调度器发出的 block ID 在所有 worker 上都有效。见 get_kv_cache_configs:1922、取最小块数:2035。

    代码摘录 3：真正分配底层设备内存

    来源 gpu_model_runner.py:6680，第 6680–6686 行：

    kv_cache_raw_tensors: dict[str, torch.Tensor] = {}
for kv_cache_tensor in kv_cache_config.kv_cache_tensors:
    tensor = torch.zeros(
        kv_cache_tensor.size, dtype=torch.int8, device=self.device
    )
    for layer_name in kv_cache_tensor.shared_by:
        kv_cache_raw_tensors[layer_name] = tensor

    这里的 int8 表示先按字节分配，不意味着模型 KV 被量化成 INT8。随后 runner 使用 spec dtype 和后端 shape/stride 创建 view，普通无 padding 分支使用 view 与 permute，而非把每个请求的 KV 再复制一份。见 reshape:6736、view/permute:6798。

    代码摘录 4：将分配结果绑定到 attention 层

    GPUModelRunner 在第 6916 行调用 bind_kv_cache；实际赋值来自 worker/utils.py:511，第 511–513 行：

    # Bind kv_caches to forward context
for layer_name, kv_cache in kv_caches.items():
    forward_context[layer_name].kv_cache = kv_cache

    这一步连接了分配出的真实 tensor 和 forward 实际使用的 attention 模块。如果某个平台只返回 spec 或处理初始化占位、没有等价的分配与绑定路径，不能据此宣称它已经实现 GPU 这条真实 KV 存储链。

    5. GPU 后端并不是一种固定物理布局

    代码摘录 5：相同语义需求，FlashAttention 与 FlashInfer 使用不同 shape

    下列两条 return 分别为原始代码；注释用于注明来源，并非把两个文件误拼为一个函数。

    # FlashAttentionBackend.get_kv_cache_shape, flash_attn.py:150
return (2, num_blocks, block_size, num_kv_heads, head_size)

# FlashInferBackend.get_kv_cache_shape, flashinfer.py:367
return (num_blocks, 2, block_size, num_kv_heads, head_size)

    来源 flash_attn.py:141、flashinfer.py:356。FlashAttention 这里要求 block size 是 16 的倍数；FlashInfer 的 NVFP4 分支还会调整末维。

    两种后端都有 get_kv_cache_stride_order()，可根据 NHD/HND 排列数据。这里 N 表示块内 token 轴、H 表示 KV head 轴、D 表示 head 维度；为避免与 num_blocks 混淆，下表将块数记为 P。

    后端返回的语义 shapeNHD 物理轴顺序HND 物理轴顺序
    FlashAttention[2,P,B,H,D][2,P,B,H,D][2,P,H,B,D]
    FlashInfer[P,2,B,H,D][P,2,B,H,D][P,2,H,B,D]

    来源 FlashAttention stride:153、FlashInfer stride:370。

    Runner 先按物理轴顺序 reshape，再用逆置换还原语义 shape，因此看到相同 tensor.shape 不代表内存布局相同；还要看 stride。例如 FlashAttention 取 P=10,B=16,H=8,D=128，以元素为单位的语义 view stride 可演算为：

    布局语义 shape对应 stride
    NHD[2,10,16,8,128][163840,16384,1024,128,1]
    HND[2,10,16,8,128][163840,16384,128,2048,1]

    这一演算只覆盖无额外 padding 的常规布局。page_size_padded 的 strided-view 分支在源码中还有“物理首维必须是 block index”的假设，不能把它泛化成任意 backend 的任意 padding 都受支持；见 gpu_model_runner.py:6780。

    6. Block table 与 slot mapping：读历史 KV 与写新 KV

    在不启用 context parallel 的普通情形，令 p 为请求内的 token position：

    [ i=\lfloor p/B\rfloor,\quad b=block_table[request,i],\quad slot=b\times B+(p\bmod B) ]

    • block_table 回答“请求的第几个逻辑块，实际在哪个物理块”。读取历史 KV 时不要求所有块连续。
    • slot_mapping 回答“本轮每个新 token 的 K/V 写到哪个槽”。它是 token 位置索引，不是 dtype 字节偏移；head、K/V 与 dtype 的具体寻址由后端完成。
    • 这些索引随调度变化，不存放在 KVCacheSpec 中。

    7. 调度器 block 与 kernel block 可以不同

    管理器希望按较大单位分配以满足容量与分组要求，attention kernel 可能只支持较小单位。当前 GPU runner 显式支持把前者拆成后者，而不是要求两者恒等。

    例如：管理器 Balloc=256，kernel Bkernel=64，一块分成 4 个 kernel blocks。管理器的 block_id=7 变为 kernel block IDs [28,29,30,31]。

    代码摘录 8：调度器块号到 kernel 块号

    来源 block_table.py:196，第 196–201 行：

    kernel_block_ids = (
    kv_manager_block_ids.reshape(-1, 1) * blocks_per_kv_block
    + kernel_block_arange
)

return kernel_block_ids.reshape(-1)

    BlockTable 要求管理器 block size 能被 kernel block size 整除；实际传给 kernel 的 table 长度随拆分扩大。见 BlockTable 初始化:47。Runner 同步扩大 kernel num_blocks、缩小每个 kernel block 的 token 维度，保持总容量不变；见 gpu_model_runner.py:6741、说明示例:6972。

    因此对比 Houmo 的编译 tile、存储块或输入 token 对齐时，应该先说明它对齐的是“调度器分配单位”还是“kernel 计算/存储单位”。名称同为 block 不等于单位相同。

    8. Prefix cache：共享的是已有结果与块引用

    CPU 的 KVCacheManager 通过 coordinator 管理各缓存组，各组有对应的 SingleTypeKVCacheManager，这些 manager 共用一个 BlockPool。见 kv_cache_coordinator.py:50。

    池管理 block_id、ref_cnt、块 hash 和 free list。开启 prefix caching 后，一个引用数为 0 的块仍可以保留已算前缀内容，并留在 free queue 中等待复用或被淘汰；“空闲可重新分配”不等于“物理数据已经清零”。

    代码摘录 9：前缀 hash 包含父块内容

    来源 kv_cache_utils.py:560，第 560–566 行：

    if not parent_block_hash:
    parent_block_hash = NONE_HASH

curr_block_token_ids_tuple = tuple(curr_block_token_ids)
return BlockHash(
    hash_function((parent_block_hash, curr_block_token_ids_tuple, extra_keys))
)

    父 hash 使“同一块 token 但前面的上下文不同”不会被当成同一个前缀结果。extra_keys 可含 LoRA、多模态标识、首块 cache salt、prompt embeddings 的信息；见 extra keys:501。实际索引还附带 group ID，避免不同缓存组误用相同 token hash；见 make_block_hash_with_group_id:53。

    举例：A 已计算完整的首 16 tokens，其首块是物理块 7；B 有同样前缀且 hash 所需条件相同，B 可以让自己的首个 block-table 项也指向 7。两者共享同一份已算 KV，只增加引用数，不复制 tensor 内容。后续不同 token 则进入各自的块。实际命中还受配置开关、跳过前缀读取标志与 attention 类型影响。

    代码摘录 10：前缀命中时增加引用数

    来源 block_pool.py:399，第 399–404 行：

    for block in blocks:
    # ref_cnt=0 means this block is in the free list (i.e. eviction
    # candidate), so remove it.
    if block.ref_cnt == 0 and not block.is_null:
        self.free_block_queue.remove(block)
    block.ref_cnt += 1

    只缓存完整块：num_full_blocks = num_tokens // block_size，见 single_type_kv_cache_manager.py:277。释放请求时减少引用计数，只有计数归零的块才回 free queue；见 block_pool.py:408。默认倒序释放请求尾部块，让尾部更早进入淘汰队列；见 single_type_kv_cache_manager.py:303。

    本版本还限制最大前缀命中长度为 request.num_tokens - 1，需要重算末尾 token 取得 logits；因块对齐限制，可能重算整个末尾块。不能说“全部 token 命中就完全跳过前向”。见 kv_cache_manager.py:213。

    9. Hybrid：分组主要服务不同缓存保留规则

    Full attention 需要历史 KV；sliding-window attention 只需要窗口内 KV。两种层即使单页字节数相同，也不应该强制使用完全相同的块保留策略。GPU V1 为组选择相应 manager，并在分配新 token 之前释放已滑出窗口的块。见 spec 到 manager 映射:1142、释放窗口外块:366。

    三个情况必须区分：

    1. 所有层同一规格：常见 Full attention 模型，一个 group、一个共享的请求 block table，各层存放自己的 KV。
    2. 同一保留规则，层容量不同：可构成 UniformTypeKVCacheSpecs；其 page_size_bytes 是组内各层页容量之和。每层 tensor 按自己的页字节数分配。见 UniformTypeKVCacheSpecs:647、相应分配:1256。
    3. 不同保留规则的普通 hybrid 路径：按兼容规格分组，统一管理单位的物理容量，并把层集合拆成适当组宽，必要时留 padding。较小页可以通过增大 block_size 来统一，但要求页容量满足实现的整除关系；见 unify_kv_cache_spec_page_size:1007、get_kv_cache_groups:1613。本地版本还有模型专用分组分支，不应只凭旧注释将“所有层每页必须相同”当作全局要求。

    一个与源码说明一致的普通 hybrid 小例子：两层 Full F0,F1，三层 Sliding S0,S1,S2，组宽取 2，则分为：

    KV group同组层独立 block table 示例
    G0F0,F1Full 组当前需要块 7
    G1S0,S2Sliding 组当前需要块 2
    G2S1,paddingSliding 组当前需要块 9

    对应只需要两条物理 tensor 池：池 0 被 F0,S0,S1 使用，池 1 被 F1,S2 使用。池中同一 block ID 的位置属于一个分配单元；不同组在同时持有 KV 时使用不同 block ID，不是多个层互相覆盖同一份 KV。源码说明见 kv_cache_utils.py:1284。

    10. 对比 Houmo 时可直接使用的检查项

    比较的是闭环，而非类名：

    环节本地 GPU V1 的实证位置Houmo 分析需要寻找的对应证据
    规格源头attention 模块生成每层 speckvspec 来自实际模型/编译产物，还是返回占位规格
    容量预算页公式 + profile + group 配置runtime 的真实 KV 字节是否纳入预算
    实际内存raw device tensor 分配芯片/设备内存由谁创建、持有和释放
    绑定forward_context[layer].kv_cache = tensorruntime 模型输入/持久缓存是否指向同一份分配
    读写定位block_table、slot_mapping 进入 kernel调度器 block ID 是否进入真实硬件读写地址转换
    共享与淘汰hash、ref count、window managerruntime 缓存生命周期是否与调度器一致
    物理格式backend shape / stride / quantization编译布局、tile、device 分片、K/V 顺序与 dtype 如何落地

    如果只有前两项成立，后面的数据通路仍须独立证明。反过来，Houmo runtime 内部自行持有缓存，也不必模仿 GPU tensor API；需要证明它实现了等价的容量、寻址和生命周期契约。
