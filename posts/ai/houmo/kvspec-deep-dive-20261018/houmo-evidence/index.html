    2. 最强证据：插件有两份脱节的 KV 配置

    2.1 调度器看到的固定描述

    plugin/model_runner.py:1318，格式化摘录（不含旁边的多层注释）：

    kv_cache_spec = {
    'model.layers.0.self_attn.attn': FullAttentionSpec(
        block_size=128,
        num_kv_heads=8,
        head_size=128,
        dtype=torch.float16,
        sliding_window=None,
    ),
}

    一个字典项，字段不从 HMM 实际层数/shape/dtype 推导。函数 docstring 称“解析 Attention module”不能替代方法体证据。:1315 还有 TODO。Pooling 覆盖方法 :4115 同样固定一层。

    plugin/worker/worker.py:265–267：

    def determine_available_memory(self) -> int:
    logger.info("szj:determine_available_memory return fixed 1024G")
    return 1024*1024*1024*1024

    返回的是 1 TiB 字节预算，没有 TCIM 内存查询。标准普通 FullAttention 单页公式得到 2 × 128 × 8 × 128 × 2 = 524288 B = 512 KiB，但这是这份逻辑声明的大小，不是实际模型一页设备内存的观测。

    plugin/worker/worker.py:297–300：

    def initialize_from_config(self, kv_cache_config: KVCacheConfig) -> None:
    """Allocate NPU KV cache with the specified kv_cache_config."""
    logger.info("szj: run initialize_from_config in houmo worker, do nothing")
    pass

    既不按配置分配设备 KV，也不向 model runner 转交配置。

    plugin/model_runner.py:888–893，省略原代码旁的误导性注释：

    kv_config = KVCacheConfig(

    :918–925 这个覆盖方法只做：

    :751–764 又将 InputBatch 的 block size 固定为 1：

    应区分三个数字：Spec 的每块 128 token、runner 本地 KV config 的块数 1、InputBatch 的块大小 1。没有一个可直接解释 HMM 的真实 KV 分配。

    3. 普通 Qwen 路径的槽位输入公式

    3.1 nblocks 是带 KV 输入的层数

    plugin/model_runner.py:928–934：

    def get_nblocks(self):
    input_names = []
    for i in range(self.prefill.get_num_inputs()):
        input_names.append(self.prefill.get_input_name(i))
    pattern = r'^model_layers_(\d+)_self_attn_kcache_input$'
    count = sum(1 for item in input_names if re.match(pattern, item))
    return count

    它数的是 K cache 输入名称的数量。对当前普通模型约定，每层对应一个 K 与一个 V，因此后面出现 2*nblocks。这个 block 接近 Transformer block，不是 vLLM KV page。对混合模型更应称“符合命名规则的 K-cache 层数”，不要自动等同全部网络层数。

    3.2 变量与编号

    • B=self.batch：decode HMM 的固定槽位数，由输入 0 shape[0] 获取（:1009）。
    • b：当前请求所在槽位。
    • N=self.nblocks：上述 K-cache 层数。
    • P=self.input_count_before_kvcache：首组 KV 前的输入项数。默认 3（:452）；发现输入 3 名为 position_ids 后设为 4（:1037–1045）。

    plugin/model_runner.py:1425–1435 的编号公式等价于：

    start = P + b * (2*N + 2)
finish = start + 2*N
prefill_input_index = P
for i in range(start, finish):
    cache = self.decode.get_dev_input(self.decode.get_input_name(i))
    self.prefill.set_input(self.prefill.get_input_name(prefill_input_index), cache)
    prefill_input_index += 1

    这是等价化简的教学片段，不宜标作逐字原文。原表达式为：

    decode_input_index_start = 2 * self.nblocks * b + self.input_count_before_kvcache + 2 * b if b > 0 else self.input_count_before_kvcache
decode_input_index_finish = 2 * self.nblocks * (b + 1) + self.input_count_before_kvcache + b * 2

    长度输入编号来自 :1057 与 :1068：

    valid_index = 1 if b == 0 else start - 2
current_index = 2 if b == 0 else start - 1

    **为什么额外有 2*b：**输入 0 是整个 decode batch 的 embedding；第一槽的两项长度在最前面的 P 中。跨过后续每个槽位时，需要跨过 2N 个 KV 输入，以及下一组两个长度输入。它不是字节偏移，也不是 token 索引。

    N=2, P=3, B=3 示例：

    槽位 bvalid 编号current 编号decode KV 编号（左闭右开）prefill KV 编号
    012[3,7)[3,7)
    178[9,13)[3,7)
    21314[15,19)[3,7)

    P=4 时首槽长度仍是 1/2，位置输入是 3，KV 才从 4 开始；后续槽仍每次只增加两个长度输入。不要把 position_ids 当每槽额外增加一个编号。

    每次循环固定绑定 2N 个对象，与 prompt token 数无关。输入列表连续不证明底层设备内存连续；该段没有验证同组 KV 输入的具体交错顺序，因此不要自行画成必然 K0,V0,K1,V1。

    3.3 加载与每请求绑定

    plugin/model_runner.py:978–1002：ordinary 路径对 prefill option 设 dummy KV 名称，加载 prefill 和 decode；:1073–1080 从 decode 取设备输入对象并传给 prefill。加载后循环所有 b，同一套 prefill 输入最后绑定到末槽。

    每次 batch>1 的 prefill 在 :1425–1435 重新选择实际槽位；batch==1 沿用初始化绑定。

    可确认事实：设备输入对象作为 set_input 参数传递。不能仅据此说“同址零拷贝”“TCIM allocator 在这里没有分配”“释放一定由 decode handle 独占负责”；这些需要 API 文档或运行时证据。

    4. 普通请求生命周期与有效长度

    阶段当前源码行为与边界
    请求建立model_runner.py:1939–1952保存 prompt、block_ids、num_computed_tokens 等 vLLM 请求状态
    入槽:2127–2138InputBatch.add_request；按得到的 req_index 重置 Houmo 槽位标志与长度
    准备 prefill:1425–1435选择该槽位的 TCIM KV 输入对象
    执行 prefill:1469–1517按固定 prefill_length 分段；填 embedding、valid/current length；run/sync
    prefill 结束:2654–2665设置该槽 context_length/current_echo_lens、prefill标记、首token/logits，并结束本轮
    单步 decode:1647–1648, :1671–1672按槽传 valid length；current length 初始化为1；执行固定 batch HMM
    请求完成:1823–1860移除请求状态、reset_relate_states、InputBatch.remove_request
    临时未调度/抢占:1886–1898从当前 batch 移出并重置槽位 CPU 状态，但保留 requests 字典中的请求对象
    恢复:2081–2098, :2127–2138更新 block IDs、重新入槽、再次重置槽位 CPU 状态；设备 KV 正确重建尚需验证

    reset_relate_states 的完整有效内容（:1805–1809）：

    def reset_relate_states(self, index):
    self.is_prefill_stage[index] = True
    self.context_lengths[index] = 0
    self.current_echo_lens[index] = 0
    self.skip_tokens[index] = 0

    没有在这个方法内清零设备 KV、擦除 prefix token 记录或释放 TCIM 页。context_lengths 与 current_echo_lens 在 :693–694 指向同一列表；单数 context_length 是另一数组，不要混写。

    model_runner.py:2142–2148：

    if 0:
    self.input_batch.condense()
    self._may_reorder_batch(scheduler_output)
self.input_batch.refresh_metadata()

    因此保留仍在跑请求的槽位位置，删除后的 None 空洞由后续适配处理。原因应写作设计解释：KV 的绑定以槽位为依据，任意移动请求行而不移动/重绑 KV 会破坏对应关系。

    prefill段10256256
    prefill段2256256512

    源码 :1481–1492 与 :1510–1517 支撑 prefill；:1067–1070 初始化 decode current=1；:1638–1648 设置 decode valid。最后一段 embedding 仍补齐256，88是有效值，不是物理 buffer capacity。

    4.2 每轮只跑一个 prefill 与进度回滚

    model_runner.py:2631–2633 选 prefill_indices[0]，:2662–2665 记录 _prefill_only_step 后结束；同轮其他 prefill 和 decode 延后。

    因此 scheduler 的计划 token 数不一定等于 runtime 本轮已计算量。插件 :3187–3211 把未执行请求输出清成空列表，设置 num_nans_dict[req_id]=-1 并回减 runner 的 num_computed_tokens。旧 04 所解释的 scheduler 私有回滚协议值得保留，但不必在 KV 主文展开所有采样细节。

    旧文还提示 _bookkeeping_sync 与当前对照 fork 签名不一致，不应把静态调用链写成“此组合已完整推理验证”。

    5. 两种 prefix 开关：未禁用、未打通、彼此独立

    5.1 vLLM enable_prefix_caching

    插件平台 platform.py:267–274：

    if cache_config.block_size is None:
    cache_config.block_size = 128
if cache_config.enable_prefix_caching and cache_config.block_size != 128:
    logger.warning("If prefix caching is enabled, block size must be set to 128.")
    cache_config.block_size = 128

    没有将 enable_prefix_caching=False，也没有验证/实现 page ID 到 TCIM KV 槽的转换。不能说“插件禁止 vLLM prefix cache”，也不能说“整个系统忽略了这个开关”。

    本地对照 fork：vllm/config/cache.py:91 默认 True；vllm/v1/core/sched/scheduler.py:227 把它传给 KVCacheManager 的 enable_caching；vllm/v1/engine/core.py:203–210 因它建立请求 block hasher。开关仍影响逻辑块复用和调度行为，问题是缺少与实际 TCIM cache 的物理衔接证据。

    额外细节：CacheConfig 默认 block size 是16、validator通常先把None改16，因此“platform里None分支=默认总是128”不严谨。prefix开关为真时第二分支才仍保证这里改128。EngineCore还可能后续根据 groups回写；应分别说明每阶段。

    5.2 Houmo enable_cacheprompt

    model_runner.py:445–467 默认 False，从 additional_config 取字符串 .lower()=="true"；不能把 JSON bool 输入已兼容当事实。

    :2494–2520 按 last_prefill_input_ids[batch_index] 比较最长公共 token 前缀。:2642–2649：

    self.common_prefix_len[index] = self._get_common_prefix_length(input_tensor, index)
self.last_prefill_input_ids[index] = input_tensor.squeeze(0).clone()
input_tensor = input_tensor[:, self.common_prefix_len[index]:]

    省略None初始化和日志。之后 prefill有效长度加common prefix，decode按对应规则加prefix。它是上一份同槽prompt的连续缓存复用，不是跨任意请求hash/refcount分页共享。

    两开关同时开启时，scheduler跳过的token与runtime真实可复用前缀是否一致尚未证实。应写“需要核对一致性”，不要无运行证据断言必然损坏输出。

    6. Qwen3.5 专用路径：不套普通槽位公式

    此处是 plugin/models/qwen3_5/houmoqwen3_5.py 内的 Qwen3_5Model。定向搜索插件源码未发现导入独立 postmo_engine / houmo_engine 包；所谓专用engine应明确指这个TCIM模型壳，避免与另一个项目的Engine/Module分层混淆。

    入口：runner model_runner.py:672–680 针对Qwen3.5经model_loader加载并set_runner；:3516–3522 经model.forward调用，不进入普通 houmo_decode。

    6.1 绑定方向与状态种类

    专用文件 :700–708 先加载prefill、为decode设置model_layers输入dummy；:731–753 从prefill拿设备对象绑定decode。与普通路径“decode对象→prefill”的方向相反。

    常规KV（:731–735）：

    if "model_layers" in input_name:
    cache = self.prefill.get_dev_input(input_name)
    self.decode.set_dev_input(input_name, cache)

    卷积状态（:736–744）：

    if "conv_cache" in input_name:
    output_name = input_name.replace("past_conv_cache_", "conv_cache_out_")
    cache = self.prefill.get_dev_input(input_name)
    self.prefill.set_dev_output(output_name, cache)
    self.decode.set_dev_input(input_name, cache)
    self.decode.set_dev_output(output_name, cache)

    recurrent_state 在:745–753有对应逻辑。源代码表达输入输出对象绑定与状态持续传递意图；底层同址/拷贝仍按TCIM API证据限定。

    外层仍只返回固定一层FullAttentionSpec，所以不能从它推出hybrid KV/Mamba配置已对接vLLM页组管理。

    6.2 prefix必须同时恢复递归状态

    • :836–854 state_cache_names含KV/conv/recurrent，但checkpoint_tensor_indices只选conv/recurrent。
    • :1008–1019 checkpoint为这些状态做clone；:1054–1094选择不晚于目标位置的最近checkpoint，copy_to恢复。
    • :1341–1413 先比较snapshot.last_processed_pos是否正好等于kv_offset；若不等，恢复checkpoint并从saved tokens补算间隙。
    • :1196–1204 即使prefix全命中，也回退最多prefill_length来重新产生有效logits；embeds路径:1247–1258同样处理。
    • :1536–1545 有prefix时绑定相应状态；没有prefix时首段执行_reset_prefill_state_to_zero清conv/recurrent，再run/sync。

    适合教学的例子：公共前缀位置750、最近state checkpoint512；复用KV本身只需保留前缀区域，但递归状态不能通过将valid_length改为750“倒回去”。需要恢复512的状态，再重放[512,750)，才能从750处理新suffix。此为依源码算法构造的示例，非运行记录。

    6.3 “per-sequence字典”不等于已支持任意并发

    虽然:878–898按batch创建state_cache和snapshot字典，当前实际入口:1159/:1188、run_prefill:1341、run_decoder:1589均写死 seq_id=0。

    此外:1146/:1182按输入长度是否大于1选择prefill/decode。不能将普通Qwen的多请求槽位调度能力直接推广成Qwen3.5的已验证能力。

    7. 容易误用的类与方法

    • plugin/attention/attention.py:16–38确实有不支持动态KV、allocate/free/swap返回True、forward为空的stub。但platform.py:284–292的恒真分支选CPU MLA/SDPA，HoumoAttentionBackend在不可达分支。应以实际TCIM load/bind/run分析，不能用stub证明当前执行能力。
    • model_runner.py:1394注释说_bind_kv_cache未调用，实际有效绑定在_load_models与prefill_func。
    • worker.py:319–321旧式determine_num_available_blocks返回(1,1)，不能混作V1 EngineCore的最终逻辑块数。
    • model_runner.py:713–720尝试按HMM修正调度容量，但:716直接标明改写时机未测；max_num_reqs还在改写前取值。文章应指向启动参数、HMM容量、InputBatch容量的协调，不宣称自动一致。
